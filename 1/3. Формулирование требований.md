# 3. Формулирование требований к системе
## 3.1. Функциональные требования

Функциональные требования описывают конкретные действия, которые пользователь может совершать в системе.   
В данной версии АРМ реализовано полное разделение прав доступа между **Администратором** и **Тех. персоналом**.

### 1. Авторизация и разграничение доступа
•   Вход в систему по идентификационным данным (логин/пароль).  
•   Предоставление прав доступа согласно роли (Администратор/Тех. персонал).  

### 2. Ведение базы гостей
•   Регистрация новых гостей и редактирование их персональной информации (ФИО, паспортные данные, контакты, адрес).  
•   Поиск и фильтрация гостей в списке.  
•   Удаление учетных записей гостей (только для роли Администратор).  

### 3. Контроль номерного фонда и бронирований
•   Формирование каталога номеров (номер, тип, стоимость, этаж, количество мест).  
•   Установление стоимости и характеристик номеров.  
•   Оформление новых бронирований для гостей.  
•   Автоматический расчет стоимости проживания на основе дат.  
•   Мониторинг статуса номеров (свободен, занят, убирается, ремонт).  
•   Редактирование и отмена существующих бронирований.  

### 4. Ведение списка технического персонала
•   Регистрация новых сотрудников (уборщиков, ремонтников) и редактирование их информации.  
•   Назначение должностей и контактных данных.  
•   Контроль персонального рабочего графика сотрудников.  

### 5. Организация и контроль графика персонала
•   Формирование сетки смен (утро, день, выходной) для каждого сотрудника.  
•   Оперативная корректировка (перенос/изменение) смен (только для Администратора).  
•   Просмотр графика персоналом (только просмотр для Тех. персонала).  

### 6. Мониторинг загрузки отеля
•   Контроль текущей загрузки номерного фонда в реальном времени (количество свободных/занятых номеров).   
•   Визуализация распределения номеров по типам и статусам.  

### 7. Генерация финансовой и статистической отчетности 
•   Генерация отчетов по выручке за выбранный период (общий доход).  
•   Анализ загруженности отеля и популярности типов номеров.  

## 3.2. Нефункциональные требования
Нефункциональные требования определяют качественные характеристики работы системы.

### Производительность
•   Время запуска приложения и первичной загрузки данных из БД SQLite не должно превышать **2 секунд**.  
•   Поиск по базе данных должен осуществляться практически мгновенно (отклик до **0.5 секунд**).  
•   Обновление графического интерфейса при переключении между вкладками должно происходить без видимых задержек.  

### Надежность и сохранность данных
•   **Целостность данных:** Применение механизмов внешних ключей (Foreign Keys) в БД, чтобы нельзя было удалить гостя, у которого есть активные бронирования, или номер, который занят.  
•   **Устойчивость к сбоям:** Система должна корректно завершать транзакции при внезапном закрытии приложения.  
•   **Надежность:** Автоматическое сохранение данных в SQLite при закрытии любой формы.  

### Удобство использования
•   **Интуитивность:** Интерфейс должен быть понятен пользователю с минимальными навыками владения ПК.  
•   **Навигация:** Наличие панели быстрого доступа к основным модулям и кнопка «Назад».  
•   **Единый стиль:** Все формы и элементы управления должны быть выполнены в едином визуальном стиле.  

### Безопасность
•   Запрет на выполнение административных функций (удаление, аналитика, управление номерами/бронированиями) для пользователей с ролью «Тех. персонал».  
•   Блокировка доступа к файлу базы данных через интерфейс приложения для неавторизованных лиц.  
•   Хранение паролей пользователей в хешированном виде.
